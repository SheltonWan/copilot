# 面向 AI 一条龙交付的需求文档编写指南

> 本文回答一个核心问题：**给 GitHub Copilot 一份需求文档，让它支撑完整交付流程（需求与原型 → 架构设计 → 项目初始化 → 功能开发 → 测试与质量 → 部署交付 → 维护迭代），这份需求文档应该写什么、怎么写、写到什么程度？**

---

## 一、核心思想：需求文档是产品意图的权威来源

AI（Copilot）无法可靠获得你没有显式提供的业务背景、约束与取舍。因此，需求文档的质量直接影响交付物的一致性和返工成本。但 PRD 不应承担所有技术事实：它负责定义产品目标、范围、业务规则和验收标准，其他产物分别对自己的领域负责。

| 信息类型 | 权威来源 |
|----------|----------|
| 产品目标、范围、业务规则、验收标准 | PRD（如 `docs/requirements.md`） |
| 架构决策及取舍 | 架构文档与 ADR |
| HTTP 接口契约 | OpenAPI/JSON Schema |
| 数据库结构与演进 | Schema 与迁移脚本 |
| 视觉规范与组件行为 | 设计系统与原型 |
| 可执行行为 | 自动化测试与实现代码 |
| 部署和运行配置 | IaC、CI/CD 与运维手册 |

发生冲突时，先确认产品意图，再更新 PRD，并同步修订受影响的契约、代码和测试，不能让多个产物长期互相矛盾。

一份合格的 AI 需求文档应满足四条标准：

1. **可验证**：每条需求都有明确的验收标准，AI 能据此生成测试用例，而不是靠猜。
2. **无歧义**：名词有定义、状态有枚举、边界有数值，不出现"尽量快""差不多""友好"这类模糊词。
3. **全覆盖**：AI 的每个交付环节（原型、架构、模块、代码、测试）都能在文档中找到对应的输入章节，不缺料。
4. **可追溯**：需求、页面、接口、数据、实现和验收证据之间能通过稳定 ID 相互追踪。

> 一个实用判断标准是：两个开发者只依赖仓库中的需求与契约，是否能对核心流程、边界条件和验收结果得出一致结论。实现细节可以不同，产品行为不应靠猜。

---

## 二、需求文档的十个核心模块（总览）

| # | 模块 | 作用 | 主要服务哪个交付环节 |
|---|------|------|----------------------|
| 1 | 产品概述与目标 | 对齐方向，明确"为什么做" | 架构设计、模块划分 |
| 2 | 用户与角色 | 定义谁在用、能做什么 | 架构设计、代码实现 |
| 3 | 功能需求清单（REQ） | 产品全量功能的权威清单 | 模块划分、代码实现、单元测试 |
| 4 | 业务流程与状态机 | 定义流转规则与状态变化 | 代码实现、集成测试 |
| 5 | 页面与交互需求 | 描述每个界面的元素与行为 | **界面原型设计** |
| 6 | 数据需求 | 定义实体、字段、关系 | 架构设计、代码实现 |
| 7 | 接口与集成需求 | 定义对内/对外契约 | 架构设计、集成测试 |
| 8 | 非功能、安全与隐私需求 | 定义性能、安全、隐私、兼容性和运维指标 | 架构设计、代码实现、部署交付 |
| 9 | 测试与验收需求 | 定义测试范围与通过标准 | 单元测试、集成测试 |
| 10 | 范围、迭代与交付约束 | 明确做什么、不做什么、如何发布 | 模块划分、架构设计、部署交付 |

版本记录、待确认问题、决策日志和需求追踪矩阵不是业务模块，但属于交付控制信息，也应包含在可直接执行的 PRD 模板中。

## 三、各模块详细写法

### 3.1 产品概述与目标

AI 需要先知道"这是什么东西"，才能做出正确的技术取舍。写清楚四点：

```markdown
## 产品概述
- 一句话定位：一款面向 [用户群] 的 [品类]，解决 [痛点]。
- 目标用户：______（谁用它）
- 核心价值：______（用户为什么愿意用/付费）
- 成功指标：______（可量化的北极星指标，如"注册后 7 日留存率 ≥ 40%"）
- 规模假设：______（用户量、峰值请求、数据量、地域和增长周期）
```

> **关键**：业务成功指标和系统规模假设要分开写。"7 日留存率"用于判断产品价值；用户量、吞吐量、数据量和增长预期才是容量与架构选型的直接输入。

### 3.2 用户与角色

用角色权限矩阵明确"谁能对什么资源做什么操作，以及能看到哪些数据"：

```markdown
## 角色与权限
| 角色 | 身份条件 | 允许操作 | 数据范围 | 额外约束 |
|------|----------|----------|----------|----------|
| 游客 | 未登录 | 浏览、搜索公开商品 | 公开数据 | 不得访问用户资料 |
| 普通用户 | 已登录且账号正常 | 下单、评论、管理个人资料 | 自己的数据 | 不得读取他人订单 |
| 运营管理员 | 已登录且具有运营角色 | 管理商品、订单和用户状态 | 所属组织数据 | 敏感操作写入审计日志 |
```

> **关键**：避免使用"全部功能、全部数据"这类宽泛授权。权限矩阵直接决定鉴权模型（RBAC/ABAC）、数据过滤规则、审计点和越权测试。

### 3.3 功能需求清单（REQ）—— 全文档最重要的一章

这是"一条龙交付"的地基。每个功能使用稳定编号（`REQ-XXX`），并写清优先级、业务规则、正常与异常流程、权限、数据影响和验收标准。

优先级要有统一口径：P0 表示缺失后核心闭环、法律合规或发布安全无法成立；P1 表示重要但可在受控条件下延期；P2 表示增强项。依赖项或高风险缓解措施即使原本是 P2，也可以因迭代目标而前移。

```markdown
## 功能需求清单

### REQ-001 用户注册
- 优先级：P0（必须）/ P1（重要）/ P2（可选）
- 用户故事：作为 [游客]，我希望 [用邮箱注册账号]，以便 [保存订单历史]。
- 前置条件：无
- 权限：仅未登录用户可访问；已登录用户提交时返回业务错误 `AUTH_ALREADY_SIGNED_IN`
- 业务规则：邮箱忽略大小写后唯一；密码 8~64 位且至少包含字母与数字；验证链接 30 分钟失效且只能使用一次
- 主流程：
  1. 用户输入邮箱、密码、确认密码
  2. 系统校验邮箱格式合法且未被注册
  3. 系统校验密码强度（≥8 位，含字母与数字）
  4. 系统发送验证邮件
  5. 用户点击邮件链接，账号激活
- 验收标准（Given-When-Then）：
  - 场景 A：Given 邮箱未注册，When 输入合法邮箱与合规密码并提交，Then 创建待激活账号并发送验证邮件
  - 场景 B：Given 邮箱已注册，When 使用该邮箱提交注册，Then 提示"该邮箱已注册"且不创建账号
  - 场景 C：Given 两次密码不一致，When 提交注册，Then 提示"密码不一致"并阻止提交
- 异常与补偿：邮件发送失败时保留待激活账号并允许重新发送；重复点击已使用链接时返回明确提示
- 数据与审计：保存用户创建时间；记录注册成功、发送失败和激活成功事件，不记录明文密码
- 依赖：REQ-005 邮件服务
```

**验收标准写法规范（Given-When-Then）**：

```markdown
Given 前置条件 / When 触发动作 / Then 预期结果
```

> **关键**：验收标准是测试设计的直接原料。每个场景都必须映射到至少一种合适的验证方式（单元、组件、契约、集成或 E2E）及可查看的验收证据，但不要求场景数与测试方法数机械地一一对应。

### 3.4 业务流程与状态机

把"跨功能"的流转规则单独写出来，避免 AI 在代码里把状态散落各处：

```markdown
## 订单状态机
| 当前状态 | 触发动作 | 目标状态 | 约束条件 |
|----------|----------|----------|----------|
| 待支付 | 支付成功 | 已支付 | 订单未过期且支付回调验签成功 |
| 待支付 | 创建后 15 分钟仍未支付 | 已取消 | 由定时任务或延迟消息触发 |
| 已支付 | 商家发货 | 已发货 | 仅商家可操作 |
| 已发货 | 用户确认收货 | 已完成 | — |
| 待支付 | 用户取消 | 已取消 | — |
```

非法流转也应定义可观察结果：

```markdown
| 当前状态 | 非法动作 | 系统响应 | 数据结果 |
|----------|----------|----------|----------|
| 已支付 | 用户取消 | HTTP 409 + `ORDER_CANNOT_CANCEL` | 状态保持已支付，不产生退款 |
| 已取消 | 支付回调 | HTTP 409 + `ORDER_EXPIRED` | 记录异常回调并进入退款/人工处理流程 |
```

> **关键**：状态机要同时写明触发者、时间事件、前置条件、目标状态、副作用和失败响应。非法流转必须说明状态是否保持不变以及是否需要退款、告警或人工补偿。

### 3.5 页面与交互需求 —— 直接决定界面原型质量

页面描述越完整，原型和实现越不需要自行补充产品决策。每个页面至少覆盖目的、权限、元素、数据来源、交互、状态、响应式规则和可访问性：

```markdown
## 页面需求

### P-01 登录页
- 页面目的：用户登录系统
- 访问与权限：仅未登录用户访问；已登录用户跳转首页
- 页面元素：
  | 元素 | 类型 | 必填 | 校验规则 | 异常提示 |
  |------|------|------|----------|----------|
  | 邮箱 | 文本框 | 是 | 邮箱格式 | "请输入有效邮箱" |
  | 密码 | 密码框 | 是 | ≥8 位 | "密码至少 8 位" |
  | 登录按钮 | 按钮 | — | — | — |
- 数据与交互：点击登录 → 调用 API-02；提交期间禁用按钮；失败时在对应字段或表单顶部显示可理解的错误
- 页面状态：初始 / 校验失败 / 提交中 / 登录失败 / 成功
- 响应式规则：手机单列；桌面内容区最大宽度 400px；320px 宽度无横向滚动
- 可访问性：输入框有可读标签；错误信息与字段关联；支持键盘操作和可见焦点；颜色对比符合 WCAG 2.2 AA
- 跳转关系：登录成功 → P-02 首页；点击"忘记密码" → P-05 找回密码
```

再补一张**全局导航结构图**：

```markdown
## 导航结构
首页 P-02
├── 商品列表 P-03 → 商品详情 P-04 → 下单 P-06
├── 个人中心 P-07
│   ├── 我的订单 P-08
│   └── 账号设置 P-09
└── 购物车 P-10
```

> **关键**：响应式要求、暗黑模式、多语言这些"界面级"需求若需要，必须显式写出，否则 AI 默认做桌面端单主题。

#### 补充：设计系统与视觉规范

界面原型能否"一次成型"，还取决于视觉层面的确定性。若产品有品牌要求，需单独写一节设计规范：

```markdown
## 设计系统
| 设计 Token | 取值 |
|------------|------|
| 主色 | #2563EB（蓝色） |
| 强调色 | #EF4444（仅用于错误/危险操作） |
| 字体 | 系统默认字体栈（-apple-system…） |
| 基础字号 | 14px；标题 18/20/24px |
| 间距单位 | 4px 基准（8/12/16/24…） |
| 圆角 | 4px（按钮）、8px（卡片） |
| 组件库 | 使用现有组件库（如 Ant Design / shadcn/ui） |
| 图标风格 | 线性图标、24×24 |
| 响应式断点 | 360 / 768 / 1280px，逐页说明布局变化 |
| 组件状态 | 默认 / hover / focus / disabled / loading / error |
| 可访问性 | WCAG 2.2 AA，键盘可达，焦点顺序符合视觉顺序 |
```

> **关键**：要么指定现成组件库，要么给出核心设计 Token。还要明确空数据、加载、错误、无权限、离线和破坏性操作确认等状态，不能只描述成功态。

### 3.6 数据需求 —— 架构设计与数据模型的原料

把核心实体、字段、关系写清楚，AI 才能生成正确的数据模型：

```markdown
## 数据需求

### 实体：用户（User）
| 字段 | 逻辑/存储类型 | 必填 | 默认值 | 索引/唯一 | 约束与数据分类 |
|------|---------------|------|--------|-----------|----------------|
| id | UUID / uuid | 是 | 系统生成 | 主键 | 不可变 |
| email | string / varchar(254) | 是 | — | 规范化后唯一 | 邮箱格式；个人信息；存储层加密；日志脱敏 |
| password_hash | string / varchar(255) | 是 | — | 否 | 仅存自适应哈希；敏感数据；禁止日志输出 |
| created_at | datetime / timestamptz | 是 | 当前时间 | 普通索引 | UTC 存储，ISO 8601 输出 |

### 实体关系
- 用户 1—N 订单（一个用户多个订单）
- 订单 1—N 订单明细（一个订单多个商品行）
- 商品 1—N 订单明细（一个商品可出现在多个订单明细中）
- 订单 N—N 商品（通过订单明细关联）

### 数据生命周期
- 所有业务记录明确所有者或租户边界，查询必须按数据范围过滤。
- 删除策略：用户发起删除后立即不可见，30 天内完成物理删除；依法保留的数据单独说明。
- 迁移策略：字段新增、回填、双写和删除需说明兼容窗口及回滚方式。
- 审计策略：记录关键状态变更的操作者、时间、来源和前后值。
```

> **关键**：除字段类型外，还要写默认值、空值、索引、外键与级联规则、租户边界、敏感级别、保留期限和迁移策略。金额必须明确币种与最小单位，时间必须明确存储时区和展示规则。

### 3.7 接口与集成需求 —— 集成测试的依据

```markdown
## 接口需求

### API-01 创建订单
- 方法：POST /api/v1/orders
- Content-Type：application/json
- 鉴权：需登录（Bearer Token）
- 幂等性：必须提供 `Idempotency-Key`；同一用户 24 小时内重复提交相同 Key，返回首次结果且不得重复扣库存
- 入参：`{ items: [{ product_id: UUID, quantity: integer >= 1 }], address_id: UUID, coupon_code?: string }`
- 成功响应：HTTP 201，`{ order_id: UUID, total_amount: integer, currency: "CNY", status: "PENDING_PAYMENT" }`；金额单位为分
- 错误体：`{ code: string, message: string, details?: object, trace_id: string }`
- HTTP 状态/业务错误码：400 `VALIDATION_ERROR` / 401 `AUTH_REQUIRED` / 404 `ADDRESS_NOT_FOUND` / 409 `OUT_OF_STOCK`
- 并发与事务：校验价格和扣减库存必须在同一事务边界内；库存冲突时整体回滚
- 副作用：创建订单成功后发布 `OrderCreated` 事件；事件投递失败不得丢失，可通过 Outbox 重试

## 第三方集成
| 系统 | 用途 | 协议 | 认证 | 超时/重试 | 失败策略 |
|------|------|------|------|-----------|----------|
| 支付宝 | 支付 | REST + 异步回调 | 密钥签名，密钥由 Secret Manager 注入 | 连接 2s、总超时 5s；仅幂等请求重试 2 次 | 标记支付处理中并通过查询任务对账 |
| 邮件服务 | 验证邮件 | HTTPS API | API Key，由 Secret Manager 注入 | 总超时 5s；指数退避重试 3 次 | 记录失败并允许用户重新发送 |
```

> **关键**：HTTP 状态码和业务错误码要分开定义。建议以 OpenAPI/JSON Schema 保存可机器校验的契约，并补齐分页、筛选、排序、版本、幂等、并发、超时、重试、限流、回调验签和副作用规则。

### 3.8 非功能、安全与隐私需求

非功能需求也要有稳定编号、测量条件和验收证据。只有数字而没有测试环境、负载模型和统计窗口，仍然无法验收：

```markdown
## 非功能、安全与隐私需求
| ID | 类别 | 可验收要求 | 验证方式 |
|----|------|------------|----------|
| NFR-001 | 性能 | 在与生产同规格的测试环境、10 万用户和 100 万订单基线数据下，以 300 RPS 持续 15 分钟；查询接口 P95 < 200ms、写接口 P95 < 500ms、错误率 < 0.1% | 固定版本压测脚本与报告 |
| NFR-002 | 可用性 | 核心 API 按自然月统计可用性 ≥ 99.9%，仅排除提前 72 小时公告的计划维护 | SLI 仪表盘与月度报告 |
| NFR-003 | 安全 | TLS 1.2+；密码使用自适应哈希；无未处理的严重/高危 SAST、依赖或镜像漏洞；登录接口限制暴力尝试 | 安全扫描、配置检查和攻击场景测试 |
| NFR-004 | 隐私 | 明确个人信息用途与保留期；支持用户数据导出和删除；日志不得包含密码、令牌或完整身份证件 | 数据清单、日志抽检和删除演练 |
| NFR-005 | 兼容性 | 支持发布日稳定版及前一个大版本的 Chrome、Safari、Edge；移动端支持 360px~430px 宽度 | 固定日期的浏览器矩阵与截图/E2E 报告 |
| NFR-006 | 可访问性 | 核心流程符合 WCAG 2.2 AA；键盘可完成操作；自动扫描无严重问题 | axe 扫描与人工键盘检查 |
| NFR-007 | 可维护性 | 核心领域分支覆盖率 ≥ 80%；Lint、类型检查和架构边界检查全部通过 | CI 报告 |
| NFR-008 | 可测试性 | 外部支付、邮件、时间和随机数依赖可替换；测试不得依赖真实生产服务 | 测试架构审查与隔离运行 |
| NFR-009 | 可观测性 | 日志含 traceId；核心 RED 指标可查询；连续 5 分钟错误率 > 1% 告警；提供 liveness/readiness | 仪表盘、告警演练和探针检查 |
| NFR-010 | 可运维性 | 配置外部化；数据库迁移向前兼容；支持优雅停机、版本回滚和审计 | 预发布部署及回滚演练 |
| NFR-011 | 灾难恢复 | 每日备份；RPO ≤ 24 小时、RTO ≤ 4 小时；每季度完成一次恢复演练 | 备份记录与恢复报告 |
```

安全需求至少覆盖：认证与授权、会话/令牌生命周期、输入校验与输出编码、CORS/CSRF、限流、防暴力破解、密钥管理、文件上传、审计日志、依赖与镜像扫描。涉及个人信息时，还要说明采集目的、合法依据、保留期限、删除与导出流程。

> **关键**：每条非功能需求都要回答"在什么环境、用什么数据、持续多久、如何测量、谁提供证据"。可观测性和可运维性不是上线后再补的功能，而是部署验收的一部分。

### 3.9 测试与验收需求

明确告诉 AI"测什么、怎么算通过"：

```markdown
## 测试需求
- 需求映射：每个 REQ/NFR 的验收场景必须在 RTM 中标明测试层级、用例和证据
- 单元测试：覆盖领域规则、边界值、异常分支与状态转换
- 组件测试：覆盖关键表单、交互状态、权限显示和可访问性；纯视觉样式不以单元测试数量为目标
- 契约测试：校验 OpenAPI、错误体、鉴权、幂等和第三方适配器契约
- 集成测试场景：
  1. 注册 → 登录 → 下单 → 支付 → 发货 全链路
  2. 库存不足时下单失败并回滚
  3. 第三方支付超时时的降级处理
- E2E 关键路径：注册、登录、下单三个用户旅程
- 安全与性能测试：执行 NFR 对应的扫描、压测和恢复演练
- 覆盖率：核心领域分支覆盖率 ≥ 80%，但覆盖率不能替代场景覆盖
- 通过标准：所有 P0 场景通过；无未处理的严重/高危缺陷；失败用例无重跑掩盖；RTM 中不存在缺少验证证据的发布范围需求
```

### 5.3 AI 澄清机制：先提问，后开工

需求文档很难一次写全。开工前应识别不确定项，但只让真正影响方向或造成不可逆后果的问题阻塞执行：

```markdown
在开始任何实现之前，请先通读本需求文档，并输出「待确认问题清单」：
1. 列出文档中所有含糊、缺失或自相矛盾之处
2. 将问题分为「阻塞」与「非阻塞」：
  - 阻塞：范围、外部契约、不可逆数据操作、安全合规、显著成本、生产发布
  - 非阻塞：命名、目录、可替换技术细节和其他可逆选择
3. 每一条写明影响的 REQ/NFR-ID、交付阶段、推荐选项和不处理的风险
4. 对阻塞问题集中提问并等待答复；对非阻塞问题记录默认假设、理由和回退方式后继续
5. 把结论写入「待确认问题与决策记录」，不要让同一问题在后续阶段重复出现
```

> **关键**：澄清机制的目标是阻止高代价误判，而不是追求文档定义每一个实现细节。集中提问、明确默认值和记录决策，才能兼顾正确性与连续执行。

下面用一个小而完整的产品做端到端示范。为控制篇幅，字段和场景数量经过压缩，但账号、CRUD、状态、提醒、API、测试、部署与范围彼此闭合。

### 范例 0. 文档控制

| 版本 | 日期 | 变更内容 | 影响面 | 状态 |
|------|------|----------|--------|------|
| v1.0 | 2026-08-30 | 定义 MVP 与迭代二 | REQ-001~REQ-006、NFR-001~NFR-005 | 已批准 |

| 决策 ID | 决策 | 理由 | 影响 |
|---------|------|------|------|
| DEC-001 | MVP 使用邮箱密码登录，不做邮箱验证和找回密码 | 保持示例闭环且控制范围 | REQ-001、P-01、API-01/02 |
| DEC-002 | 删除采用软删除，用户端不可恢复，30 天后物理删除 | 支持误操作排查与隐私删除流程 | REQ-005、DATA-002 |

### 范例 1. 产品概述

- 一句话定位：一款面向个人用户的轻量待办 Web 应用，帮助用户快速记录、整理并完成任务。
- 目标用户：使用现代桌面或移动浏览器的个人用户，不包含团队协作场景。
- 核心价值：3 秒内记下任务，清楚看到未完成与已完成事项；迭代二增加到期提醒。
- 成功指标：`user_registered` 事件后 2 分钟内触发 `todo_created` 的用户比例 ≥ 60%；注册后第 7 天触发登录或待办操作事件的用户比例 ≥ 30%；数据来自产品事件仓库，按自然周统计。
- 规模假设：MVP 预计 1 万月活、峰值 50 RPS、累计 100 万条待办，部署在单一区域。
- 名词："完成"表示任务状态为 `COMPLETED`；"删除"表示用户端不可见的软删除，不等于立即物理清除。

### 范例 2. 用户与角色

| 角色 | 身份条件 | 允许操作 | 数据范围 | 额外约束 |
|------|----------|----------|----------|----------|
| 游客 | 未登录 | 注册、登录 | 无业务数据 | 不得访问待办接口 |
| 注册用户 | 已登录且账号正常 | 查看、新增、编辑、完成、重新打开、删除待办，设置提醒 | 仅自己的待办 | 所有查询和更新必须校验 `user_id` |

### 范例 3. 功能需求清单

**REQ-001 注册与登录**（P0，MVP）
- 用户故事：作为游客，我希望使用邮箱和密码创建账号并登录，以便在不同设备访问自己的待办。
- 业务规则：邮箱规范化后唯一；密码 8~64 位且至少包含字母与数字；同一 IP 与规范化邮箱组合连续 5 次失败后限流 15 分钟；访问令牌有效期 30 分钟、仅保存在内存中，MVP 不提供刷新令牌，过期后重新登录；退出登录时立即清除本地令牌。
- 验收标准：
  - Given 邮箱未注册，When 提交合法邮箱和密码，Then 创建账号、记录 `user_registered` 并直接进入 P-02，响应中不得返回密码或哈希。
  - Given 邮箱已注册，When 再次注册，Then 返回 409 `EMAIL_ALREADY_EXISTS` 且不创建账号。
  - Given 密码错误，When 尝试登录，Then 返回统一认证失败提示且不泄露邮箱是否存在。
  - Given 用户已登录，When 点击退出，Then 清除内存中的访问令牌并跳转 P-01；后续受保护请求返回 401。

**REQ-002 创建与查看待办**（P0，MVP）
- 用户故事：作为注册用户，我希望创建并查看自己的待办，以便记录要做的事。
- 业务规则：标题去除首尾空格后长度为 1~100 个字符；新待办状态为 `ACTIVE`；列表按 `created_at` 倒序分页。
- 验收标准：
  - Given 已登录，When 提交合法标题，Then 创建成功、记录 `todo_created` 并出现在未完成列表顶部。
  - Given 标题为空或超过 100 个字符，When 提交，Then 显示字段错误且不创建记录。
  - Given 用户 A 与用户 B 各有待办，When 用户 A 查询列表，Then 只返回用户 A 的数据。

**REQ-003 编辑待办**（P0，MVP，依赖 REQ-002）
- 业务规则：仅可编辑自己的非删除待办；标题规则与创建一致；并发更新使用版本号检测冲突。
- 验收标准：
  - Given 待办属于当前用户，When 修改为合法标题，Then 保存成功并更新 `updated_at` 与 `version`。
  - Given 客户端版本已过期，When 提交编辑，Then 返回 409 `TODO_VERSION_CONFLICT` 且不覆盖新数据。

**REQ-004 完成与重新打开**（P0，MVP，依赖 REQ-002）
- 验收标准：
  - Given 存在 `ACTIVE` 待办，When 用户勾选完成，Then 状态变为 `COMPLETED`、记录 `completed_at` 并移入已完成区。
  - Given 存在 `COMPLETED` 待办，When 用户取消勾选，Then 状态恢复为 `ACTIVE`、清空 `completed_at` 并回到未完成区。

**REQ-005 删除待办**（P0，MVP，依赖 REQ-002）
- 业务规则：`ACTIVE` 和 `COMPLETED` 均可删除；删除后用户端不可恢复；30 天后物理删除。
- 验收标准：Given 待办属于当前用户，When 确认删除，Then 状态变为 `DELETED`、记录 `deleted_at`，并立即从所有列表消失。

**REQ-006 到期提醒**（P1，迭代二，依赖 REQ-002）
- 业务规则：使用 Web Push；时间以 UTC 存储、按用户 IANA 时区展示；`reminded_at` 防止重复发送；完成或删除的待办不发送提醒。
- 验收标准：
  - Given 用户已授权通知且待办仍为 `ACTIVE`，When 到达 `remind_at`，Then 60 秒内只发送一次通知并记录 `reminded_at`。
  - Given 用户拒绝通知权限，When 设置提醒，Then 显示"浏览器通知未开启"及设置入口，不重复弹出权限请求。
  - Given 待办在提醒前已完成或删除，When 到达提醒时间，Then 不发送通知。

### 范例 4. 状态机

| 当前状态 | 触发动作 | 目标状态 | 数据副作用 |
|----------|----------|----------|------------|
| `ACTIVE` | 标记完成 | `COMPLETED` | 写入 `completed_at` |
| `COMPLETED` | 重新打开 | `ACTIVE` | 清空 `completed_at` |
| `ACTIVE` | 确认删除 | `DELETED` | 写入 `deleted_at`，取消提醒 |
| `COMPLETED` | 确认删除 | `DELETED` | 写入 `deleted_at` |

| 当前状态 | 非法动作 | 系统响应 | 数据结果 |
|----------|----------|----------|----------|
| `DELETED` | 编辑/切换状态 | 404 `TODO_NOT_FOUND` | 不修改数据 |
| 任意状态 | 操作他人的待办 | 404 `TODO_NOT_FOUND` | 不泄露资源是否存在 |

### 范例 5. 页面、导航与设计系统

导航：P-01 注册/登录页 → P-02 待办列表页；P-02 通过抽屉打开 P-03 编辑待办。

| Token/规则 | 取值 |
|------------|------|
| 组件库 | shadcn/ui，图标使用 Lucide |
| 色彩 | 主色 `#2563EB`；错误色 `#DC2626`；正文与背景对比度 ≥ 4.5:1 |
| 间距/圆角 | 4px 基准；按钮 4px；面板 8px |
| 响应式 | 360px 起单列；768px 起列表最大宽度 720px；不得横向滚动 |
| 可访问性 | WCAG 2.2 AA；键盘可完成注册、创建、编辑、切换和删除 |

**P-01 注册/登录页**
- 元素：模式切换、邮箱、密码、提交按钮；字段错误与输入框关联。
- 状态：初始、校验失败、提交中、认证失败、成功；提交中按钮禁用且布局不跳动。
- 跳转：成功 → P-02；已登录访问 P-01 → P-02。

**P-02 待办列表页**
- 元素：快速新增输入框、未完成列表、已完成折叠区、分页加载、退出按钮。
- 状态：加载骨架、空列表、加载失败并重试、离线提示、正常列表。
- 交互：Enter 创建；勾选切换状态；编辑按钮打开 P-03；删除按钮先确认。

**P-03 编辑待办抽屉**
- 元素：标题、提醒时间（迭代二）、保存和关闭按钮。
- 状态：初始、校验失败、保存中、版本冲突、保存成功；冲突时允许刷新最新数据。

### 范例 6. 数据需求

**DATA-001 User**

| 字段 | 类型 | 必填 | 索引/唯一 | 约束 |
|------|------|------|-----------|------|
| id | UUID | 是 | 主键 | 系统生成 |
| email | varchar(254) | 是 | 规范化后唯一 | 个人信息；存储层加密；日志脱敏 |
| password_hash | varchar(255) | 是 | 否 | 自适应哈希；禁止日志输出 |
| timezone | varchar(64) | 是 | 否 | IANA 时区，默认 `UTC` |
| created_at | timestamptz | 是 | 否 | UTC |

**DATA-002 Todo**

| 字段 | 类型 | 必填 | 索引/唯一 | 约束 |
|------|------|------|-----------|------|
| id | UUID | 是 | 主键 | 系统生成 |
| user_id | UUID | 是 | 组合索引 | 外键 → User；所有权边界 |
| title | varchar(100) | 是 | 否 | 去除首尾空格后 1~100 字符 |
| status | enum | 是 | 组合索引 | `ACTIVE/COMPLETED/DELETED` |
| remind_at | timestamptz | 否 | 提醒扫描索引 | UTC；仅迭代二使用 |
| reminded_at | timestamptz | 否 | 否 | 防止重复提醒 |
| completed_at | timestamptz | 否 | 否 | 仅完成状态有值 |
| deleted_at | timestamptz | 否 | 否 | 软删除时间 |
| version | integer | 是 | 否 | 默认 1；乐观锁 |
| created_at / updated_at | timestamptz | 是 | created_at 索引 | UTC |

实体关系：User 1—N Todo；删除 User 时先完成用户数据导出流程，再级联删除其 Todo。`DELETED` Todo 每日清理，满 30 天物理删除。

### 范例 7. 接口与集成

所有接口使用 `/api/v1`、JSON 和统一错误体 `{ code, message, details?, trace_id }`；除注册和登录外均需 Bearer Token。

| ID | 方法与路径 | 请求摘要 | 成功响应 | 关键错误 |
|----|------------|----------|----------|----------|
| API-01 | POST `/auth/register` | email、password | 201 + access_token、expires_in、user | 400、409 `EMAIL_ALREADY_EXISTS`、429 |
| API-02 | POST `/auth/login` | email、password | 200 + access_token、expires_in、user | 401 `INVALID_CREDENTIALS`、429 `LOGIN_RATE_LIMITED` |
| API-03 | GET `/todos?status=&cursor=&limit=` | limit 1~100 | 200 + items、next_cursor | 400、401 |
| API-04 | POST `/todos` | title；迭代二增加 remind_at | 201 + Todo | 400、401；支持 `Idempotency-Key` |
| API-05 | PATCH `/todos/{id}` | title?/status?/version；迭代二增加 remind_at | 200 + Todo | 400、401、404、409 `TODO_VERSION_CONFLICT` |
| API-06 | DELETE `/todos/{id}` | `If-Match: version` 请求头 | 204 | 401、404、409 |

第三方集成：迭代二使用 Web Push 服务；VAPID 私钥由 Secret Manager 注入；请求总超时 5 秒，幂等重试 3 次；持续失败时记录指标并在应用内显示提醒失败状态。

### 范例 9. 测试与验收

- 单元测试：标题边界、密码规则、状态转换、30 天清理条件、时区转换和乐观锁。

## 八、需求变更与版本管理

一条龙交付中最常见的坑不是"写不出来"，而是"写到一半需求变了"。因此文档本身也要被管理：

```markdown
## 版本记录
| 版本 | 日期 | 变更人 | 变更内容 | 影响面 |
|------|------|--------|----------|--------|
| v1.0 | 2026-08-30 | 张三 | 初始版本 | 全部 |
| v1.1 | 2026-09-02 | 李四 | 新增 REQ-007 导出功能 | API-04、P-10、DATA-03、测试与部署配置 |
| v1.2 | 2026-09-05 | 张三 | 修改 REQ-001 校验规则 | P-01、API-01、REQ-001 测试与用户文案 |
```

**变更时的增量重做提示词**：

```markdown
需求文档已从 v1.1 更新到 v1.2，本次变更内容如下：
[粘贴版本记录的"变更内容"和"影响面"]

请只重做受影响的交付环节（列出影响面），其余已完成部分保持不变：
- 先通过版本差异、依赖和 RTM 校验直接与间接影响，不能只依赖人工填写的影响面
- 若影响 REQ/接口：更新契约、实现及对应层级的测试
- 若影响页面：更新设计系统/原型、前端实现和组件/E2E 测试
- 若影响状态机/数据：更新迁移、回滚方案、集成测试和运行监控
- 完成后更新 RTM、决策记录和验收证据，并列出未覆盖的风险
```

> **关键**：影响面能显著提高增量修改的准确性，但不能替代依赖分析和版本差异。变更记录至少引用受影响的 REQ/NFR/API/PAGE/DATA-ID，并由 AI 用代码搜索和测试结果验证。

## 九、MVP 与迭代拆分策略

用优先级把全量需求切成"第一版可交付的最小集"，分批发给 AI，比一次性交付更可控：

| 迭代 | 范围 | 目标 |
|------|------|------|
| MVP（v1.0） | 全部 P0 + 构成闭环所需的依赖与安全合规项 | 走通核心闭环，可演示、可验证 |
| 迭代二 | 剩余 P1 | 补齐重要功能 |
| 迭代三 | 其余增强项 | 根据数据反馈提升体验或效率 |

拆分规则：
1. P0 原则上进入 MVP；若无法进入，必须重新定义 MVP 或记录明确的降级与批准结论。
2. 安全、合规、数据完整性以及 P0 的技术依赖不因原优先级较低而自动后置。
3. P2 通常后置，但若它是低成本前置依赖或能显著降低交付风险，可以提前。
4. 每个迭代必须形成独立用户闭环，并有范围、验收证据、发布和回滚条件。
5. 一个迭代对应一次可验收的增量交付，不要求一次处理整份大文档。

> **关键**：MVP 优先能显著降低 AI 一次做多导致的质量稀释。**先交付一个小而完整的产品，再迭代扩功能。**

---

## 十、需求追踪矩阵（RTM）

RTM 把"需求 → 设计/契约 → 实现 → 验证 → 证据"串成一张表，贯穿交付全程，方便验收时逐条核对：

```markdown
## 需求追踪矩阵
| ID | 迭代 | 需求 | 设计/接口/数据 | 实现位置 | 验证层级与用例 | 验收证据 | 状态 |
|----|------|------|----------------|----------|----------------|----------|------|
| REQ-001 | MVP | 创建待办 | P-02、API-04、DATA-002 | src/todo/create.ts | 单元 + 契约 + E2E | CI #128、验收截图 | 完成 |
| REQ-002 | MVP | 标记完成 | FLOW-001、API-05 | src/todo/toggle.ts | 单元 + 集成 | CI #128 | 完成 |
| NFR-001 | MVP | 列表性能 | API-03、ADR-002 | src/todo/query.ts | 性能测试 | perf-2026-08-30.html | 完成 |
| REQ-003 | 迭代二 | 到期提醒 | API-05、DATA-002、DEC-002 | src/remind/worker.ts | 单元 + 集成 + E2E | — | 待实现 |
```

> **关键**：每个发布范围内的 REQ/NFR 都必须有适合它的验证方式和证据。代码需求应指向实现与自动化测试；文档、合规或运营要求可以指向审批记录、扫描报告、演练报告等证据，不能为了填表强行制造代码或单元测试。

## 十一、落地到项目仓库：与 Copilot 工作流衔接

这份 PRD 不是孤立文档，应作为项目的第一块基石落地：

```
项目根目录
├── docs/
│   ├── requirements.md      ← 本 PRD 落在这里
│   ├── design-system.md
│   ├── runbook.md
│   └── adr/
├── .github/
│   └── copilot-instructions.md  ← 指向 PRD 的固定约定
├── openapi.yaml
├── migrations/
├── infra/
└── src/ ...                 ← AI 生成的代码
```

在 `copilot-instructions.md` 中固定一条约定，让 AI 每次开工都先读 PRD：

```markdown
# 项目约定
- `docs/requirements.md` 是产品目标、范围、业务规则和验收标准的权威来源。
- 架构决策以 `docs/adr/` 为准，HTTP 契约以 `openapi.yaml` 为准，数据库结构以迁移脚本为准；发生冲突时先确认产品意图并同步修订相关产物。
- 任何实现和验证证据必须能追溯到 REQ/NFR-ID。
- 需求变更须先更新 requirements.md 的版本与影响面，再更新契约、实现和测试。
- 每个 REQ/NFR 完成后同步更新需求追踪矩阵（RTM）及验收证据。
```

与七阶段交付流程的对应关系：

| 交付流程阶段 | PRD 提供的输入 |
|--------------|----------------|
| 1 需求立项 | 本文档即该阶段的产出 |
| 2 架构设计 | 第 3.6 数据 + 3.7 接口 + 3.8 非功能 |
| 3 项目初始化 | 技术约束（3.10） |
| 4 功能开发 | 第 3.3 功能清单 + RTM |
| 5 测试与质量 | 第 3.9 测试需求 + 验收标准 |
| 6 部署交付 | 可观测性/可运维性（3.8）+ 部署与运行约束（3.10） |
| 7 维护迭代 | 版本记录 + 决策日志 + RTM + 运行指标 |

> **关键**：PRD 写好后，把它交给"从零到一交付流程"作为阶段 1 的输入；后续六阶段依据自动门禁推进，并在架构签核和生产发布等风险节点保留人工确认。

## 十二、常见错误与陷阱

| 错误写法 | 问题 | 正确写法 |
|----------|------|----------|
| "系统响应要快" | 无法验证 | "在生产同规格环境和指定基线数据下，以 300 RPS 持续 15 分钟，核心查询 P95 < 200ms、错误率 < 0.1%" |
| "界面要友好" | 无客观标准 | "表单校验失败时，字段下方红字提示具体原因" |
| "支持用户管理" | 边界不清 | "管理员可新增、停用、重置用户密码" |
| 只写正常流程 | 异常场景缺失 | 补充：输入非法、权限不足、依赖失败、并发冲突 |
| 验收标准写成"应该能注册" | 不可测试 | 用 Given-When-Then 写可执行场景 |
| 状态流转只写正向 | 逆向/非法流转缺失 | 明确哪些流转被禁止 |
| 数据字段不写约束 | AI 自由发挥 | 写明类型、必填、唯一、精度、单位 |
| 接口只写 400/401 等数字 | 无法区分业务失败，集成测试断言不稳定 | 同时定义 HTTP 状态、业务错误码和统一错误体 |
| 把 PRD 当作所有技术事实的唯一来源 | 契约、迁移与实现容易互相覆盖 | 为 PRD、ADR、OpenAPI、迁移脚本和部署配置划分权威边界 |
| 所有不确定项都阻塞提问 | Agent 频繁停顿，无法连续交付 | 仅阻塞高风险决策；可逆选择记录假设后继续 |
| 一个验收场景等于一个单元测试 | 测试层级错配或为了数量拆测试 | 将场景映射到合适的单元、组件、契约、集成或 E2E 验证 |
| 性能指标只有一个数字 | 缺少环境、负载和统计口径，无法复现 | 同时写明环境、数据量、请求模型、持续时间、分位数和错误率 |

## 十三、交付前质量检查清单

提交给 Copilot 前，逐项打勾确认：

- [ ] 每个功能都有 `REQ-XXX` 编号和可测试的验收标准
- [ ] 已定义名词、规模假设、角色动作、数据范围和权限约束
- [ ] 每个 REQ 都写了业务规则、异常/补偿、数据影响和依赖
- [ ] 每个页面都写了权限、元素、校验、页面状态、响应式和可访问性
- [ ] 核心状态机写全正向、逆向、时间事件、非法流转、副作用和失败响应
- [ ] 数据实体写明类型、空值、默认值、索引、关系、租户边界、敏感级别、保留和迁移策略
- [ ] 接口写全 Schema、鉴权、HTTP 状态、业务错误码、幂等、并发、分页、超时和副作用
- [ ] 非功能需求都有 ID、量化目标、测试环境、数据规模、统计窗口和证据形式
- [ ] 安全、隐私、备份恢复、可观测性和可运维性均有可执行要求
- [ ] 设计系统、响应式断点和可访问性标准已明确
- [ ] 测试层级、覆盖范围、缺陷门禁和通过标准已明确
- [ ] 范围外清单已列出，约束与假设已写明
- [ ] 已划分 MVP 与迭代范围，并纳入安全合规项及 P0 的必要依赖
- [ ] 已定义部署环境、密钥注入、迁移、回滚、监控、告警和运维手册
- [ ] 已建立完整日期的版本记录、变更影响面和决策日志
- [ ] 已建立覆盖 REQ/NFR 的 RTM，并预留验证方式与验收证据
- [ ] 已规划分级澄清机制，区分阻塞问题和可逆默认假设
- [ ] 已明确 PRD、ADR、OpenAPI、迁移脚本、设计系统和部署配置的权威边界
- [ ] 除反例引用外，全文无"尽量、大概、差不多、友好"等模糊表述

---

> 一句话总结：**把 PRD 写成可验证的产品契约，再用 ADR、OpenAPI、迁移脚本、设计系统、测试和部署配置承接技术事实，Copilot 才能从需求与原型一路推进到部署和维护。**
