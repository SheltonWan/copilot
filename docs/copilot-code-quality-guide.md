# GitHub Copilot 代码质量与错误风险控制指南

> **目标**：建立一套可重复、可验证的 Copilot 代码实现流程，降低逻辑错误、异常错误、回归错误和运行失败的概率。
>
> **核心结论**：无法通过任何规则保证绝对零错误，但可以让错误更早暴露、影响范围更小、修复过程可追踪，并降低错误进入生产环境的概率。

## 1. 正确理解“零错误”

### 1.1 为什么不能保证零错误

即使代码通过了类型检查、Lint、测试和人工审查，也可能因为以下因素在运行时出错：

- 需求本身不完整或存在歧义
- 测试没有覆盖某种输入组合
- 生产配置与开发环境不同
- 外部 API、数据库或消息队列发生异常
- 并发、时序和网络问题难以在本地复现
- 依赖升级后出现未预期的兼容性变化
- 用户行为超出原有假设

因此，不应把“Copilot 生成了代码”视为“代码已经正确”。Copilot 是实现、分析和审查流程中的参与者，不能替代可执行验证和责任审查。

### 1.2 更可靠的工程目标

将目标从“零错误”调整为以下四点：

1. **错误尽早暴露**：在编辑器、类型检查、单元测试或 CI 阶段发现问题。
2. **错误容易定位**：保留清晰的失败信息、测试证据和变更边界。
3. **错误影响可控**：使用超时、重试、回滚、权限控制和灰度发布。
4. **错误能够学习**：将线上问题转化为回归测试、项目规则或监控指标。

## 2. 四道质量关卡

Copilot 代码实现建议统一遵循以下流程：

```mermaid
flowchart LR
    A[需求澄清] --> B[局部代码分析]
    B --> C[最小修改]
    C --> D[针对性验证]
    D --> E[完整质量门禁]
    E --> F[人工审查]
    F --> G[灰度发布]
    G --> H[监控告警与回滚]
    H --> I[沉淀回归测试和规则]
```

| 关卡 | 必须回答的问题 | 主要手段 |
|------|----------------|----------|
| 修改前 | 需求是什么？哪些代码真正控制行为？ | 调用链、类型、配置、测试分析 |
| 修改中 | 是否采用最小变更？异常路径是否完整？ | 小步编辑、强类型、输入校验 |
| 修改后 | 这次修改是否真的解决问题？ | 针对性测试、Lint、类型检查、构建 |
| 合并发布前 | 是否可能引入回归或生产风险？ | CI、人工审查、集成测试、灰度和监控 |

### 2.1 质量门禁原则

- 任一必要检查失败，不得进入下一道关卡。
- 第一次验证失败后，优先修复同一代码路径，并重新运行相同检查。
- 不得通过删除、跳过、降低断言或放宽规则来“修复”失败。
- 不能运行某项检查时，必须明确记录原因和剩余风险。
- 关键模块不能只依赖 Copilot 自审，必须有人类审查者负责确认。

## 3. Copilot 实现标准流程

### 第一步：把任务写成可验收的目标

任务描述至少应包含：

- 功能目标
- 不在本次范围内的内容
- 输入和输出
- 成功条件
- 失败条件
- 兼容性要求
- 需要更新的测试或文档

示例：

```text
为订单查询接口增加按状态筛选功能。

范围：仅修改查询参数解析、服务层过滤和相关测试，不修改数据库表结构。
输入：status 可选，只允许 pending、paid、cancelled。
成功：未传 status 时保持原有查询行为，传入合法 status 时返回对应订单。
失败：非法 status 返回 400，不应访问数据库。
兼容性：已有调用方和分页参数行为保持不变。
验收：通过参数校验、服务层单元测试、接口集成测试和构建检查。
```

### 第二步：先分析，不立即编辑

要求 Copilot 先读取并说明：

- 当前入口和调用方
- 真正决定行为的函数或模块
- 相关类型和数据结构
- 配置、环境变量和外部依赖
- 现有测试及其覆盖范围
- 可能受影响的公共接口

分析后必须形成一个可证伪的假设，例如：

> 假设：错误来自服务层将缺失的 `status` 当作空字符串过滤，而不是来自控制器参数解析。验证方式：检查服务层调用参数，并运行不传 `status` 的现有接口测试。

### 第三步：选择最小修改方案

优先级如下：

1. 修复根因，而不是在异常结果上增加表面判断。
2. 保持公共接口和现有行为兼容。
3. 复用项目已有的校验、错误类型、日志和测试工具。
4. 只修改完成任务所需的文件。
5. 不在同一轮混入无关重构、依赖升级或格式化变更。

### 第四步：先建立或补充测试

对于新行为，先写能够失败的测试；对于明确 Bug，先增加能够复现问题的回归测试。测试应说明它防止哪一种回归，而不是只追求覆盖率数字。

### 第五步：实现并立即验证

完成第一处实质性修改后，立即执行最便宜且最能证伪当前假设的检查：

- 纯逻辑变更：目标单元测试
- 类型或接口变更：类型检查或编译
- 参数校验变更：接口测试
- 数据库变更：迁移检查和集成测试
- 前端交互变更：组件测试或端到端测试

不要在第一次验证前继续扩展修改范围。

### 第六步：完成全量门禁和审查

局部检查通过后，再运行项目完整测试、构建、依赖扫描和必要的人工审查，最后才进行合并或发布。

## 4. 实现前规则

### 4.1 上下文规则

Copilot 修改代码前，必须优先确认：

- 调用方是否依赖当前返回值或异常类型
- 被调用方是否可能返回空值、不完整数据或异常
- 配置是否可能缺失、格式错误或使用默认值
- 数据库查询是否涉及事务、并发和分页
- 外部请求是否设置超时和取消机制
- 当前项目采用什么日志、错误和测试模式

### 4.2 需求不明确时的处理

遇到以下情况，不能自行假设后直接修改：

- 同一个字段有多个可能含义
- 未说明失败时应返回什么结果
- 不清楚是否需要保持旧接口兼容
- 不清楚数据删除、覆盖或迁移策略
- 不清楚权限边界
- 不清楚外部服务失败时是否重试

应先列出歧义，并把每项歧义转化为选项、假设或待确认问题。

### 4.3 变更边界规则

每次任务开始前，明确：

```text
允许修改：<列出文件、模块或行为>
禁止修改：<列出不应触及的部分>
兼容要求：<列出现有接口和行为>
完成标准：<列出可执行检查>
```

这样可以降低 Agent 因上下文扩展而产生无关修改的风险。

## 5. 实现中规则

### 5.1 强类型优先

- 不随意使用 `any`、未检查的类型断言或强制转换。
- 对函数参数和返回值声明明确类型。
- 对外部输入使用运行时 schema 校验。
- 不把静态类型声明当作运行时数据验证。
- 让非法状态难以被创建，而不是在多个调用点重复兜底。

### 5.2 显式处理状态转换

涉及订单、支付、任务、审批等流程时，使用明确的状态机或受限枚举，禁止通过随意拼接字符串推动状态变化。每个状态应明确允许的下一状态和失败处理方式。

### 5.3 不吞掉异常

禁止以下做法：

```ts
try {
  await doSomething();
} catch {
  // 什么也不做
}
```

必须明确异常策略：

- 可恢复错误：是否重试、重试次数和退避策略
- 不可恢复错误：如何返回、记录和告警
- 事务错误：是否回滚或补偿
- 用户错误：返回可理解且不泄露敏感信息的提示
- 系统错误：记录足够上下文，但不记录密钥、令牌和密码

### 5.4 外部依赖必须有边界

网络、数据库、文件系统、消息队列和第三方 SDK 都是不可靠边界，至少应考虑：

- 超时
- 取消
- 重试是否会造成重复操作
- 幂等键或去重策略
- 连接和资源释放
- 返回数据校验
- 依赖不可用时的降级或快速失败

### 5.5 保持修改可回滚

避免将多个不可逆操作放在同一流程中。涉及数据变更时，优先设计：

- 事务边界
- 回滚方式
- 数据备份
- 向后兼容的迁移步骤
- 失败后的补偿任务

## 6. 异常与边界处理清单

每个新增或修改的功能，至少逐项检查以下内容：

### 输入边界

- `null`、`undefined` 或缺失字段
- 空字符串、空数组、空对象
- 类型错误或格式错误
- 超长字符串和超大数值
- 负数、零、最大值和最小值
- 非法日期、时区和夏令时
- 重复参数、重复记录和重复提交

### 业务边界

- 无数据时的行为
- 数据已存在时的行为
- 资源不足时的行为
- 状态不允许转换时的行为
- 权限不足和资源不存在的区别
- 并发修改导致版本冲突时的行为

### 运行边界

- 网络失败和连接超时
- 数据库不可用或事务回滚
- 第三方接口返回 4xx、5xx 或不完整数据
- 配置缺失或环境变量格式错误
- 进程重启、任务重复执行和消息重复消费
- 内存、磁盘、连接池或文件句柄耗尽

### 安全边界

- 未授权访问
- 越权访问其他用户或租户数据
- SQL 注入、命令注入和路径穿越
- XSS、CSRF 或不安全反序列化
- 日志泄露敏感信息
- 错误信息泄露内部实现细节

## 7. 测试与自动化质量门禁

### 7.1 测试层次

| 测试类型 | 主要目标 | 适用范围 |
|----------|----------|----------|
| 单元测试 | 验证纯逻辑和边界条件 | 计算、转换、校验、状态机 |
| 集成测试 | 验证模块与真实依赖的协作 | 数据库、缓存、消息队列、外部接口适配 |
| 接口测试 | 验证输入输出和错误契约 | HTTP API、RPC、事件消费 |
| 端到端测试 | 验证关键用户流程 | 登录、下单、支付、审批等核心流程 |
| 契约测试 | 防止服务间接口不兼容 | 微服务和第三方接口 |

### 7.2 最低测试矩阵

每个业务功能至少覆盖：

| 场景 | 必须验证的内容 |
|------|----------------|
| 正常路径 | 正确输入得到预期结果 |
| 空值路径 | 缺失或空输入不会导致未捕获异常 |
| 边界路径 | 最小值、最大值和特殊值行为正确 |
| 失败路径 | 依赖失败时返回正确错误，不泄露内部信息 |
| 权限路径 | 未登录、无权限和越权访问被正确阻止 |
| 重复路径 | 重复请求不会造成重复写入或重复扣款 |
| 回归路径 | 原有行为和兼容接口保持不变 |

### 7.3 CI 质量门禁

不同项目的命令不同，但通常应包含：

```bash
# 格式和静态质量
npm run format:check
npm run lint

# 类型和编译
npm run typecheck

# 测试和构建
npm test
npm run build

# 依赖安全检查
npm audit --audit-level=high
```

后端项目还应根据技术栈增加数据库迁移检查、启动检查、接口契约测试和集成测试。命令名称必须以项目实际脚本为准，不应盲目复制示例。

### 7.4 测试失败处理规则

1. 先确认失败是否由本次修改引起。
2. 读取完整错误信息、堆栈和失败测试上下文。
3. 在同一代码路径上修复根因。
4. 使用相同命令重新验证。
5. 只有局部验证通过后，才扩大到完整测试。
6. 若测试暴露的是原有问题，不要擅自扩大任务范围，应记录并单独处理。

## 8. 代码完成后的反向审查

实现完成后，使用以下问题审查 diff：

### 行为审查

- 是否改变了未要求修改的原有行为？
- 是否保持公共接口、错误码和数据格式兼容？
- 是否遗漏调用方、类型定义、配置或文档更新？

### 逻辑审查

- 条件判断是否覆盖所有分支？
- 是否存在空值、越界、精度、时区或排序问题？
- 循环、递归和分页是否可能无法结束？
- 并发执行时是否会重复、覆盖或丢失数据？

### 异常审查

- 是否存在空的 `catch` 或被忽略的 Promise？
- 是否设置了合理的超时？
- 重试是否可能放大副作用？
- 资源是否在成功和失败路径都能释放？
- 错误是否被正确分类、记录和返回？

### 安全审查

- 是否信任了未经校验的外部输入？
- 是否新增了权限绕过、注入或敏感信息泄露风险？
- 是否硬编码了密钥、令牌、密码或环境配置？

### 变更审查

- 是否存在无关文件修改？
- 是否加入了不必要的抽象或依赖？
- 是否能用更小的改动完成同一目标？
- 测试是否真正验证了行为，而不是只验证代码被执行？

## 9. 可直接复制的 Copilot 提示词

### 9.1 修改前分析

```text
请先分析当前代码，不要立即修改文件。

任务目标：<描述目标>
允许范围：<描述允许修改的文件或模块>
禁止范围：<描述不可修改的部分>

请读取相关调用方、被调用方、类型定义、配置和现有测试，并回答：
1. 当前行为是什么？
2. 哪个函数或模块真正控制该行为？
3. 期望行为是什么？
4. 可能受影响的调用方和公共接口有哪些？
5. 正常、边界和异常场景有哪些？
6. 最小修改方案是什么？
7. 哪个最便宜的检查可以证伪你的根因假设？

分析完成后等待确认，再开始修改。
```

### 9.2 测试优先实现

```text
请先根据当前项目的测试框架设计并添加测试，覆盖：
- 正常路径
- 缺失和非法输入
- 边界值
- 外部依赖失败
- 权限失败
- 重复调用或并发场景
- 原有行为回归

每个测试请说明它防止哪一种回归。
先运行测试确认新测试能够按预期约束行为，再实现最小代码修改。
```

### 9.3 完成后的反向审查

```text
请审查刚才的修改，重点查找实际问题，不要只给总体评价。

请按严重程度列出：
1. 原有行为是否被意外改变
2. 未处理的异常和边界路径
3. 空值、类型、越界、精度和时区风险
4. 超时、重试、幂等、事务和资源释放问题
5. 并发、重复提交和数据一致性问题
6. 权限、注入和敏感信息泄露问题
7. 遗漏的调用方、测试、配置和文档更新
8. 是否存在更小且更符合项目风格的实现

每个问题都要指出文件、代码位置、风险和建议修复方式。
如果没有发现问题，也要列出尚未验证的风险和缺失测试。
```

### 9.4 验证结果汇报

```text
请执行与本次修改直接相关的最小验证，然后再执行项目完整质量门禁。

汇报格式：
- 修改内容：
- 运行的命令：
- 每条命令的结果：
- 修复过的失败：
- 尚未运行的检查及原因：
- 尚存风险：
- 是否建议合并：是/否，以及理由

不要用“应该没问题”代替实际验证结果。
```

## 10. 项目级指令模板

可以将以下规则加入项目的 `.github/copilot-instructions.md`，再根据技术栈调整命令和目录：

```md
## 代码实现质量规则

1. 修改代码前，先读取相关调用方、被调用方、类型定义、配置和测试。
2. 修改前先说明当前行为、预期行为、根因假设和最便宜的验证方式。
3. 每次只处理一个明确问题，优先采用最小变更。
4. 不明确的需求、错误返回、权限边界或兼容性要求必须先列出并确认。
5. 新增或修改业务逻辑时，必须同步新增或更新正常、边界、异常和回归测试。
6. 必须处理空值、非法输入、外部依赖失败、超时、重试、资源释放和权限失败。
7. 不得吞掉异常，不得使用空的 catch 块，不得忽略未处理的 Promise。
8. 不得硬编码密钥、令牌、密码或环境相关配置。
9. 不得在未确认调用方兼容性的情况下修改公共接口、错误码或数据格式。
10. 首次修改后，立即运行与改动直接相关的最小验证。
11. 验证失败时，先修复同一代码路径并重新运行相同检查。
12. 不得为了通过检查而删除、跳过、弱化测试或放宽质量规则。
13. 完成前必须运行项目可用的类型检查、Lint、测试和构建命令。
14. 最终汇报修改内容、实际运行的命令、结果、未验证项目和剩余风险。
15. 高风险模块必须增加人工审查、集成测试、回滚方案和发布后监控。
```

项目规则应当是流程约束，不应写成无法验证的口号。例如“保证代码绝对正确”不可执行；“修改后必须运行类型检查和目标测试”可以执行和审计。

---

## 11. 高风险模块控制要求

以下模块需要提高质量门槛：

- 身份认证、授权和多租户隔离
- 支付、订单、余额和财务计算
- 数据删除、迁移和批量更新
- 文件上传、下载和解析
- 并发任务、定时任务和消息消费
- 公共 API、SDK 和跨服务契约
- 密钥、令牌和个人敏感信息处理
- 生产部署和基础设施配置

除常规质量门禁外，建议增加：

| 控制项 | 目的 |
|--------|------|
| 双人审查 | 降低单人或单 Agent 判断错误 |
| 更强的集成测试 | 验证真实依赖和事务行为 |
| 幂等和回滚设计 | 防止重复执行和不可逆损坏 |
| 审计日志 | 支持问题追踪和责任确认 |
| 灰度发布 | 限制错误影响范围 |
| 监控和告警 | 及时发现异常趋势 |
| 快速回滚 | 缩短故障恢复时间 |

## 12. 发布、监控与持续改进

### 12.1 发布前

- 确认构建产物来自已验证的提交。
- 确认配置、数据库迁移和依赖版本与目标环境一致。
- 确认回滚步骤可执行，而不是只存在于文档中。
- 确认关键指标、日志和告警已经准备好。

### 12.2 发布后

重点观察：

- 错误率和异常类型变化
- 响应时间和超时比例
- 数据库、缓存和消息队列健康度
- 重试次数、重复请求和失败任务数量
- 关键业务转化或完成率

### 12.3 事故后的知识沉淀

每次线上问题至少产出一项改进：

- 一个回归测试
- 一条静态检查或 Lint 规则
- 一条项目级 Copilot 指令
- 一项监控或告警
- 一处类型、校验或接口契约改进
- 一条运行手册或回滚步骤

这样规则不会停留在文档中，而会逐步进入代码和自动化流程。

## 13. 最终检查表

### 修改前

- [ ] 目标、范围和验收条件已明确
- [ ] 调用链、类型、配置和测试已读取
- [ ] 已识别正常、边界、异常和安全场景
- [ ] 已形成可验证的根因假设
- [ ] 已确定最小修改方案

### 修改中

- [ ] 修改范围没有无故扩大
- [ ] 输入已校验，外部数据已验证
- [ ] 异常没有被吞掉
- [ ] 超时、重试、幂等和资源释放已考虑
- [ ] 公共接口和兼容行为未被意外破坏
- [ ] 测试已同步新增或更新

### 修改后

- [ ] 目标测试通过
- [ ] 类型检查通过
- [ ] Lint 和格式检查通过
- [ ] 集成测试或接口测试通过
- [ ] 构建通过
- [ ] 依赖安全检查已完成
- [ ] 已完成反向代码审查
- [ ] 未运行的检查和剩余风险已记录
- [ ] 高风险模块已完成人工审查和发布控制

## 结语

减少 Copilot 代码错误的关键，不是让模型承诺“永远正确”，而是建立一个模型无法绕过的验证闭环：

```text
先理解 -> 小步实现 -> 立即验证 -> 完整门禁 -> 人工审查 -> 灰度发布 -> 监控回滚 -> 沉淀规则
```

只要每个环节都有明确输入、可执行检查和失败处理，Copilot 就能从“代码生成器”变成受工程流程约束的开发协作者。这样可以大幅降低错误风险，但任何严谨的工程系统都应诚实保留对未知风险的认识。
