# 多人开发项目的 AI 记忆同步指南

> **目标**：让多个开发者、多个 VS Code 工作区和多个 Copilot 会话共享同一套可靠的项目知识，同时保留个人偏好和临时上下文的独立性。

## 1. 先理解一个关键边界

多人开发时，不要把某个开发者电脑上的 AI 记忆目录当成团队数据库。个人记忆、会话记忆和仓库记忆通常受本地环境、账号和编辑器状态影响，未必会自动同步给其他成员。

因此应采用下面的原则：

> **团队共识进入 Git，个人偏好留在个人环境，临时过程保留在会话中。**

凡是“其他成员也需要知道，并且未来仍然有效”的信息，都应该整理成仓库内可审查的文件。这样 Copilot、人工开发者和 CI 都能读取同一份事实来源。

### 1.1 三类信息的判断方式

| 信息类型 | 示例 | 推荐位置 | 是否提交 Git |
|----------|------|----------|--------------|
| 团队事实 | 架构、目录、构建命令、接口约定 | `AGENTS.md`、`.github/copilot-instructions.md`、`docs/` | 是 |
| 个人偏好 | 个人快捷键、跨项目习惯、个人提示词 | 用户级 Copilot/VS Code 配置 | 否 |
| 临时状态 | 当前任务假设、未完成排查、一次性日志 | 当前会话、Issue、Draft PR | 通常否 |

### 1.2 共享记忆不等于复制全部聊天记录

聊天记录往往包含错误假设、重复讨论和敏感信息。同步时应提炼“结论 + 依据 + 影响”，而不是把整段对话直接提交到仓库。

## 2. 记忆分层模型

建议使用四层模型管理团队知识：

```text
个人层       用户偏好、个人工具配置
会话层       当前任务的计划、临时假设、未完成事项
项目层       项目约定、架构事实、开发命令
决策层       经过评审的技术决策、业务规则和长期约束
```

### 2.1 项目层

项目层内容应短小、稳定、容易被 Agent 自动读取。例如：

- 如何安装依赖、运行、测试和构建
- 哪个目录负责 API、数据访问和页面
- 命名、错误处理、日志和测试规范
- 不允许修改的兼容性约束
- 本地开发所需但不包含秘密值的环境变量说明

### 2.2 决策层

涉及架构、数据库、公共 API 或安全边界的结论，建议使用 ADR（Architecture Decision Record）保存：

```text
docs/decisions/
├── ADR-001-database-choice.md
├── ADR-002-api-error-format.md
└── ADR-003-authentication-boundary.md
```

每份 ADR 只描述一个决策，并保留状态：`提议`、`已接受`、`已废弃`或`已替代`。

### 2.3 本地仓库记忆目录

如果当前 Agent 环境提供仓库记忆目录，它可以帮助本机 Copilot 快速恢复上下文，但不要假设它天然具备团队同步能力。关键内容仍应复制到仓库文件，并通过 Pull Request 审查。

## 3. 推荐的仓库结构

一个适用于多数项目的最小结构如下：

```text
.github/
└── copilot-instructions.md   # 项目级 AI 行为规则

AGENTS.md                     # 跨 AI 工具和开发者通用规则

docs/
├── ai-context.md             # 项目事实、命令和术语
├── decisions/                # 长期技术决策
│   └── ADR-001-example.md
└── runbooks/                 # 可重复执行的操作手册
    ├── local-development.md
    └── release.md
```

### 3.1 文件职责不要重叠

| 文件 | 应该写什么 | 不应该写什么 |
|------|------------|--------------|
| `AGENTS.md` | 所有开发者和 AI 都要遵守的通用规则 | 长篇架构背景、临时任务状态 |
| `.github/copilot-instructions.md` | Copilot 的项目上下文、行为要求和验证要求 | 个人偏好、密码和 Token |
| `docs/ai-context.md` | 项目事实、命令、目录和术语 | 强制性规则的多个互相矛盾副本 |
| `docs/decisions/ADR-*.md` | 一个长期技术决策及其取舍 | 未确认的想法清单 |
| `docs/runbooks/*.md` | 可按步骤重复执行的操作 | 只对某个人电脑有效的临时命令 |

### 3.2 控制上下文大小

共享指令不是项目百科全书。将最常用、最重要的约束放在入口文件，把详细背景拆到 `docs/`，并用链接指向它们。过长、重复或互相冲突的指令会降低 Agent 的判断质量。

## 4. 共享记忆的写作规范

### 4.1 每条记忆包含四个要素

```markdown
## API 错误格式

- 结论：所有 HTTP API 使用 `ApiError` 返回结构化错误。
- 依据：客户端统一根据 `code` 和 `message` 处理错误。
- 影响：新增接口必须复用共享错误类型，不直接返回任意 JSON。
- 维护：接口契约变更时同步更新本节和相关测试。
```

这四个要素分别回答：是什么、为什么、会影响什么、什么时候需要更新。

### 4.2 区分事实、规则和建议

- **事实**：当前系统使用 PostgreSQL 作为主数据库。
- **规则**：生产代码不得直接读取数据库连接密码。
- **建议**：新增查询优先放在 Repository 层。

不要把未经确认的建议写成事实，也不要把临时 workaround 写成长期架构规则。

### 4.3 使用明确、可验证的措辞

推荐：

```markdown
- 安装依赖：`pnpm install`
- 单元测试：`pnpm test`
- 提交前必须运行：`pnpm lint && pnpm test`
```

避免：

```markdown
- 通常可以用包管理器安装依赖。
- 代码质量要尽量保证。
```

### 4.4 记录来源和更新时间

对容易变化的信息添加来源和维护标记：

```markdown
> 来源：ADR-004；最后确认：2026-08-31；维护人：平台组
```

维护人是责任归属，不是唯一编辑者。任何成员都可以提交修改，但高风险决策应由指定责任人确认。

## 5. 团队同步工作流

### 5.1 新成员初始化

```bash
git clone <repository-url>
cd <repository>
git pull --ff-only
```

进入项目后，先阅读以下文件：

1. `AGENTS.md`
2. `.github/copilot-instructions.md`
3. `docs/ai-context.md`
4. 与当前任务相关的 ADR 和操作手册

然后让 Copilot 执行一次上下文确认：

```text
@workspace 阅读项目级指令和 docs/ai-context.md，列出：
1. 当前项目的安装、测试和构建命令
2. 与我这次任务相关的目录和架构约束
3. 你发现的任何冲突或过期信息
先不要修改文件。
```

### 5.2 开发过程中发现新知识

按下面的顺序处理：

```text
发现事实 → 用测试、代码或文档确认 → 判断影响范围
→ 写入合适的共享文件 → 提交 Pull Request → 审查合并
```

不要只对 Copilot 说“记住这个”，因为这可能只写入当前账号或当前环境，其他成员无法稳定获得。

### 5.3 Pull Request 约定

当代码变更改变了项目行为、命令或架构时，Pull Request 应明确说明：

- 是否需要更新 `AGENTS.md` 或 `.github/copilot-instructions.md`
- 是否需要新增或更新 ADR
- 是否需要更新操作手册
- 哪些旧记忆已失效
- 验证命令及结果

可以在 Pull Request 模板中增加：

```markdown
## AI 上下文影响

- [ ] 不影响共享上下文
- [ ] 已更新项目指令
- [ ] 已更新 `docs/ai-context.md`
- [ ] 已新增或更新 ADR
- [ ] 已更新操作手册
```

### 5.4 分支与同步节奏

- 开始工作前：`git pull --ff-only`
- 修改共享记忆前：确认分支基于最新主分支
- 合并前：解决文档冲突，并检查是否产生重复规则
- 合并后：通知团队拉取最新指令和文档
- 高变动项目：在 CI 中检查链接、命令和 Markdown 格式

## 6. 冲突与过期信息治理

### 6.1 信息冲突的处理顺序

当两个文件出现矛盾时，按以下顺序确认：

1. 运行中的代码、测试和构建配置
2. 已接受且未废弃的 ADR
3. 项目级指令
4. 普通说明文档
5. 个人记忆和聊天结论

最终应修复文档本身，不能要求每个成员在脑中记住“某条规则例外”。

### 6.2 过期信息不要静默保留

废弃内容应明确标记并链接到替代内容：

```markdown
> 状态：已废弃。请改用 [ADR-006](./ADR-006-new-approach.md)。
```

确认替代方案已经生效后，再删除无价值的旧文档，避免 Agent 同时读取两个相反结论。

### 6.3 定期维护

建议每个迭代或每月检查一次：

- 命令是否仍能执行
- 目录和模块名称是否仍存在
- ADR 状态是否准确
- 文档中的链接是否有效
- 规则是否在代码和测试中得到体现
- 是否出现个人环境路径、秘密值或内部 Token

## 7. 安全边界

共享记忆中禁止出现：

- 密码、API Key、Access Token、Cookie
- 私钥、证书私密部分和签名材料
- 生产数据库连接串中的秘密值
- 个人电脑的敏感路径、账号和隐私数据
- 未经授权的客户数据或业务数据样本

可以记录：

- 环境变量名称
- 脱敏后的配置示例
- Secret 的存放位置和申请流程
- 本地启动所需的非敏感默认值

示例：

```env
DATABASE_URL=postgresql://<user>:<password>@<host>:5432/<database>
```

`.env`、部署凭据和签名文件应通过 `.gitignore`、Secret 管理系统和访问控制保护。共享文档只描述获取方式，不保存秘密本身。

## 8. 可直接使用的模板

### 8.1 `AGENTS.md` 模板

```markdown
# 项目开发规则

## 常用命令

- 安装：`<command>`
- 开发：`<command>`
- 测试：`<command>`
- 构建：`<command>`

## 目录约定

- `<directory>`：<responsibility>
- `<directory>`：<responsibility>

## 必须遵守

- <rule>
- <rule>

## 修改后的验证

- <validation command>
```

### 8.2 `.github/copilot-instructions.md` 模板

```markdown
---
description: "项目级 AI 编程规则和上下文"
---

# 项目上下文

## 工作方式

- 先阅读相关代码和文档，再修改文件。
- 修改后运行与变更范围匹配的测试或检查。
- 不要猜测接口、环境变量或业务规则；缺少依据时提出问题。

## 代码约定

- <convention>
- <convention>

## 验证命令

- <command>

## 参考资料

- [项目上下文](../docs/ai-context.md)
- [技术决策](../docs/decisions/)
```

### 8.3 ADR 模板

```markdown
# ADR-XXX：<决策标题>

- 状态：提议 / 已接受 / 已废弃 / 已替代
- 日期：YYYY-MM-DD
- 责任人：<team or role>

## 背景

<需要解决的问题和约束>

## 决策

<最终选择>

## 取舍

### 优点

- <benefit>

### 缺点

- <cost>

## 影响

<对代码、测试、部署和后续开发的影响>

## 相关资料

- <link or file>
```

## 9. 交付前检查清单

### 共享内容

- [ ] 团队必须知道的结论已经写入 Git 管理的文件
- [ ] 个人偏好和临时会话状态没有混入项目规则
- [ ] 事实、规则和建议已明确区分
- [ ] 关键技术决策有对应 ADR

### 一致性

- [ ] 构建、测试和启动命令可以实际执行
- [ ] 文档与代码、测试和配置没有矛盾
- [ ] 旧决策已标记废弃或链接到替代方案
- [ ] 没有重复且互相冲突的规则

### 安全

- [ ] 没有密码、Token、私钥或真实客户数据
- [ ] 环境变量只记录名称和脱敏示例
- [ ] 本地敏感配置没有被加入 Git

### 协作

- [ ] 文档变更已通过 Pull Request 审查
- [ ] Pull Request 已说明 AI 上下文是否受影响
- [ ] 合并后团队成员可以通过 Git 拉取同一份知识

---

## 结语

多人开发中的“AI 记忆同步”，本质上是团队知识管理问题。最可靠的方案不是同步每个人的聊天历史，而是把稳定、可验证、可审查的项目知识写成版本化文档，并让代码、测试、ADR 和操作手册共同维护它。

个人记忆可以帮助开发者提高效率；Git 中的项目文档，才是团队共同依赖的事实来源。
